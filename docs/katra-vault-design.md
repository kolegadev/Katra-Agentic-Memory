# Katra Vault — Secure Secret Storage & Agent Authentication

- **Spec version:** v1.0
- **Status:** Approved (design only — no code written)
- **Date:** 2026-09-03
- **Author:** Lilly (with John)
- **Applies to:** `kolegadev/Katra-Agentic-Memory`, informed by `kolegadev/Secure-Vault`

## 1. Purpose and objectives

Katra currently has two security gaps:

1. **No encrypted secret storage.** Memory content is plaintext in MongoDB — the only
   `node:crypto` usage in the server is hashing / random bytes / constant-time compare
   (no ciphers). Secrets stored as ordinary memories sit in `semantic_facts` in plaintext.
2. **Static bearer keys on agent machines.** Each agent holds a long-lived client key
   (`~/.katra/keys/katra-<user>.key`); a compromised machine yields full identity access
   to private and team memory indefinitely.

**Katra Vault** closes these gaps and achieves three objectives:

- **O1 — Encrypted-at-rest secret store native to Katra**, replacing the VeraCrypt-USB
  workflow for operational convenience and DB/backup exfiltration protection.
- **O2 — RBAC / partition-scoped access**: a secret is private to one agent (`user_id`
  partition) or shared across the team (`shared_id` partition), with **per-service
  approval** required to *use* it.
- **O3 — No secret ever passes through an LLM**: secrets are excluded from the memory LLM
  pipeline, reads never return raw values to a model, and use happens server-side through
  capability tools.

## 2. Findings (research summary)

### 2.1 Secure-Vault (OpenClaw)

Node/Express + React over a VeraCrypt/LUKS-mounted USB volume. Concepts reused here:
**redaction** (values never echoed), **service linking** (secret → service), **profile-based
ACLs**, and the **Signing Agent** (a restricted process that uses a secret and returns only
results). Its encryption is whole-volume — files are plaintext while mounted — so Katra
improves on it with field-level encryption.

### 2.2 Katra internals (verified against source)

- **Identity** — `resolveCallerIdentity()` maps the presented key
  (`X-MCP-Auth` / `Authorization: Bearer` / `?token=`) to a `user_id`; client keys are stored
  as SHA-256 hashes only (`server/src/utils/api-key-manager.ts`).
- **Partitions** — `resolveWriteScope()` (`services/memory/write-scope-policy.ts`) returns
  `{user_id, shared_id}`; `PERSONAL_KINDS` are forced private; everything else defaults to
  `shared_id: 'my-team'` unless `private: true`. Reads use `buildScopeFilter()`
  (`memory-scope-service.ts`) = caller's own private + `my-team` shared.
- **Trust boundary** — `caller.trusted` (loopback / admin key) vs untrusted (mapped client
  key, pinned to its own identity).
- **Storage** — MongoDB + Redis + MinIO, no encryption at rest. The background processor
  (extraction, summarization, sleep consolidation, reflection) calls a pluggable remote LLM
  and can include memory content.
- **Dashboard** — `katra-server` serves `/dashboard/` with API-key and LLM-config
  management: the natural home for secret entry.

## 3. Locked decisions

1. **Master key in `.env`** (`KATRA_VAULT_MASTER_KEY`, generated by `install.sh`).
   No external KMS; no Secure-Vault USB for storage.
2. **TOTP-first** agent auth (RFC 6238, Google Authenticator), QR enrollment.
3. **Per-identity auth policy** (§6 table).
4. **Per-service approval** for secret use (§7.3).
5. **Migration defers hard-delete** of legacy plaintext secrets; keys may be rotated
   out-of-band by John.

## 4. Data model

New MongoDB collection `secrets`:

```jsonc
{
  "secret_id": "lilly/agentmail-api-key",   // <scope>/<name>
  "name": "agentmail-api-key",
  "owner": { "user_id": "lilly" },           // private partition
  //  or  { "shared_id": "my-team" },          // team partition
  "acl": { "readers": ["lilly"] },           // optional finer grain (defaults to owner)
  "service": "agentmail",                    // service linking (Secure-Vault)
  "kind": "api_key",                         // api_key | password | token | totp_secret | env
  "envelope": {
    "alg": "aes-256-gcm",
    "kek_version": 1,
    "iv": "<b64>", "tag": "<b64>",
    "ciphertext": "<b64>",                   // encrypted secret value
    "dek_wrapped": "<b64>"                   // DEK wrapped by the scope KEK
  },
  "meta": {
    "created_by": "lilly", "created_at": "<ts>",
    "updated_at": "<ts>", "last_used_at": "<ts>",
    "rotation_due_at": "<ts>"
  },
  "flags": { "rotatable": true, "approval_required": true }
}
```

Additional collections: `vault_approvals` (identity × service grants), `vault_audit`
(value-free audit trail), `auth_sessions` (short-lived session tokens), `auth_totp`
(enrolled TOTP secrets, encrypted, `kind: totp_secret`).

## 5. Encryption

Envelope encryption using `node:crypto` only (no new dependencies):

- **Master key** `KATRA_VAULT_MASTER_KEY` = 32 random bytes (64 hex), in `.env`, generated
  once by `install.sh`.
- **Scope KEK** = `HKDF-SHA256(master_key, info = "vault:" + ("user:"+user_id | "shared:"+shared_id), 32)`
  → **crypto-enforced partition isolation**: a raw DB dump cannot decrypt a scope it lacks
  the KEK for.
- **Per-secret DEK** = 32 random bytes.
- **Value** encrypted with the DEK via AES-256-GCM (random 12-byte IV, auth tag).
- **DEK wrapped** with the scope KEK via AES-256-GCM.
- `kek_version` allows future master-key rotation (re-wrap DEKs, keep ciphertexts).

## 6. RBAC / scoping (reuse Katra machinery)

- **Write** — mirror `resolveWriteScope`: `scope: team` → `{shared_id: my-team}`;
  `scope: private` → `{user_id: caller.user_id}`. Untrusted callers are always pinned to
  their own identity. Operator provisioning (dashboard) is trusted and may name any scope.
- **Read** — mirror `buildScopeFilter`: caller sees own private + `my-team` shared secrets;
  never another identity's private partition. Per-secret `acl.readers` allows finer grants
  (default = owner).
- **Use** (capability tools) — requires an active `vault_approvals` grant for
  `(identity, service)` (§7.3).

## 7. No secret through the LLM (O3) — three hard guards

### 7.1 Pipeline denylist

The `secrets`, `vault_approvals`, `vault_audit`, `auth_sessions`, and `auth_totp`
collections are **denylisted** from the background processor, embedding, semantic
extraction, summarization, sleep consolidation, reflection, knowledge-graph synthesis,
pattern detection, and operational distillation. Enforced by an explicit collection
denylist in the ingestion/processing scan, plus a security test asserting no LLM call ever
receives a denylisted document.

### 7.2 No-value-to-model reads

`vault_get_secret` returns `{secret_id, name, scope, service, length, last_used_at, status}`
with `value: "<redacted>"`. Raw values are never serialized into an MCP tool result or log.

### 7.3 Capability tools + per-service approval

Secrets are only *used* server-side:

- **Generic** `vault_http(secret, method, url, inject_header, body?)` — the server resolves
  the secret, injects it into the outbound request, and returns the response body only.
- **Per-service drivers** (AgentMail, gcloud, …) expose typed operations (`email_send`,
  `email_read`, …) with no key in the signature.
- **Per-service approval** — a secret may only be used through a capability tool if the
  calling identity holds an active approval `(identity, service, expires_at)`. Approvals are
  granted by a human in the dashboard (which requires the human's admin session), carry an
  expiry (default 30d), and are revocable. Every use is written to `vault_audit`
  (who, service, operation, outcome, timestamp — never the value).

## 8. Agent authentication (TOTP)

Replaces "static key = permanent access" with enrollment + short-lived sessions.

- **Enrollment (one-time, human)** — dashboard creates an identity → server generates a TOTP
  secret (base32) → shows a QR (`otpauth://totp/Katra:<user>?secret=…&issuer=Katra`) → the
  human scans it into Google Authenticator. The TOTP secret is stored encrypted
  (`kind: totp_secret`, that identity's private partition), never in the LLM.
- **Session bootstrap** — the static client key becomes a **bootstrap credential only**: it
  may *request* a session, but a valid 6-digit TOTP code is required to issue a short-lived
  session token (default TTL 12h, per-identity `session_ttl`). TOTP is verified per RFC 6238
  (HMAC-SHA1, 30s window, ±1 step, replay-guarded).
- **Per-identity policy**:

| Identity class | Auth | Compromise mitigation |
|---|---|---|
| **Interactive** — `shoshin`, `zanshin`, `lilly` (laptops/iMac, human present) | TOTP-gated, short-lived sessions | stolen key useless without TOTP; token expiry |
| **Unattended** — satori heartbeat loop, `gas-law-watcher` | device-bound long-lived credential, least-privilege scope | narrow job scope; rotation; anomaly detection; instant revocation |
| **Trusted** — loopback / admin key (thebrick) | loopback trusted; admin key rotated + shorter-lived | admin key rotation |

## 9. Surface (MCP + REST)

MCP tools: `vault_put_secret` (operator only), `vault_list_secrets`, `vault_get_secret`
(redacted), `vault_delete_secret`, `vault_rotate_secret`, `vault_approve_service`,
`vault_revoke_approval`, `vault_http` / `vault_invoke` (capability, approval-gated),
`vault_audit`, `auth_enroll_totp` (returns QR), `auth_issue_session` (TOTP → token).

REST: `/api/v1/vault/*` and `/api/v1/auth/*`, admin-key gated for admin operations.

## 10. Migration

On ship (Phase 3): import the AgentMail key (from `~/.katra/keys/agentmail-lilly.key`,
operator-side) into the vault; hard-delete the two legacy plaintext `semantic_facts`
AgentMail docs and their embeddings; rotate the key (John rotates if desired). Audit other
plaintext secrets currently in shared memory (notably the home WiFi passwords in the Tivat
network notes) and decide whether to vault them.

## 11. Threat model

**Protects against:** DB/backup exfiltration (envelope + per-scope KEK); cross-identity read
(scope filter + crypto); LLM training leakage (denylist + no-value + capability); log
leakage (redaction + value-free audit); compromised agent machine for *interactive*
identities (TOTP + short sessions); stolen static key (useless without TOTP);
unattended-agent abuse (least privilege + anomaly detection + revocation).

**Not fully protected:** host root compromise reading the in-memory master key; a
compromised agent abusing its already-approved services (audited + revocable, not
prevented); operator provisioning if ever exposed to agents (mitigated by operator-only
`vault_put_secret`).

## 12. Phasing

1. **Vault core** — `secrets` collection, envelope crypto, `.env` master key, dashboard
   entry form, scope RBAC, value-free audit.
2. **No-LLM guarantees** — pipeline denylist + security test.
3. **Capability + migration** — `vault_http` + per-service drivers, per-service approval,
   migration + rotation of legacy secrets.
4. **TOTP auth** — enrollment QR, session issuance, per-identity policy, revocation.
5. **Optional** — USB cold backup/recovery; Okta/OIDC; KMS for hosted tier; dashboard polish.

## 14. Future feature suggestions (not in v1.0 scope)

Ideas raised in design review and captured here for later; they do not change the v1.0
sections above until a decision is made.

### 14.1 Ephemeral local-LLM exception (opt-in)

Relax O3 for exactly one deliberate human workflow: when a human genuinely needs to
*work through* a secret with an agent (debugging, setup), allow it only inside a:

- **locally hosted** session — the model runs on the operator's own machine, never a
  remote LLM;
- **ephemeral** session — nothing persists: no conversation history, no memory-pipeline
  writes, no embeddings/summarization, no value logging;
- **gated + audited** session — explicit per-session opt-in (admin session required),
  with an audit event recording that a value became model-visible.

The §7.1 denylist stays untouched because such a session never writes to the pipeline.

### 14.2 Human OAuth for service delegation

Keep TOTP for identity bootstrap (§8), and delegate *service access* with standard
OAuth instead of the custom `vault_approvals` table: the agent requests a grant via the
OAuth device flow, a human approves it on their device, and the grant (scoped, expiring,
revocable at the IdP) authorizes capability-tool use (§7.3). Better revocation and
delegation than a bespoke approvals table; costs an IdP (self-hosted or external), which
tensions with the no-new-dependency constraint. If adopted, `vault_approve_service` /
`vault_revoke_approval` become device-flow initiation / revocation.

### 14.3 Secret name obfuscation

Two layers, both defense-in-depth:

- **At rest** — `name`, `service`, `scope`, `acl`, and `meta` ride in an encrypted
  `meta_blob` under the scope KEK, so a raw DB dump does not reveal the secret
  inventory; optionally an opaque `secret_id` (e.g. `v_8f3a2d`) so even lookup keys carry
  no service identity.
- **At runtime** — for integrations that need real env vars (codex, gcloud, CLIs), a
  vault launcher resolves the secret and injects it under a randomly named variable
  (e.g. `KATRA_RND_9f3ab2d1`, regenerated per session/machine) and templates the tool
  config to match, so nothing on the machine exposes `OPENAI_API_KEY=sk-…`.

Caveat: neither layer stops an attacker who can read process memory or intercept the
outbound request — the capability-tool model (§7.3) remains the primary guard. At-rest
obfuscation only helps against DB/backup exfiltration, not repo leaks (source still
names the services).
